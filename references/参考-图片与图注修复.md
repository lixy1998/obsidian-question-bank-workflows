# 参考-图片与图注修复

> 适用场景：从 MinerU 解析源 md 抽题录入时，出现「图注丢失 / 空 alt / 图片本体缺失 / 孤儿图配对」等问题的定位与修复。
> 依据 2026-09-19「河南《解析与检测》2026 下册综合检测 8 套」录入实测沉淀；示例中路径均为占位符，实际以当次会话临时目录为准。

---

## 一、polish 图注删除机制与空行躲避法

**问题形态**：pass2 JSON 题干里明明有图注文字行（如「贾湖骨笛\n河南出土\n距今 8 000 多年」），build 后入库笔记里却消失。

**根因**：build 侧选择题题干清洗函数 `polish_choice_stem` 会删除「图注/年代注释残留行」，删除条件为**全部满足**：

1. 行非空
2. 不含图片语法 `![`
3. 不含作答括号 P
4. 非表格行（不以 `|` 开头/结尾）
5. `len(st) <= 24`
6. **上一行是图片行**（`out[-1]` 含 `![`）

**躲避法**：在 pass2 中把「图片行\n图注行」改为「**图片行\n空行\n图注行**」——处理图注行时 `out[-1]` 是空行，条件 6 不满足，图注行存活。空行随后被 polish 第③步清理，最终题干无空行，不影响成品。

**连带效应**（利用而非规避）：
- 图注行与作答括号同行（如「残存的圆明园文渊阁藏《四库全书》（　　）」）时，条件 3 已使其天然存活，无需处理；
- polish 第③步「删除所有 P → 末行后补 P（末行是图片/表格/占位说明则另起一行）」会自动把 P 安放到正确位置，定点替换时 P 可交给 polish 处理。

**定点修复范式**（fix_captions.py 结构，幂等）：

1. 源 md 建立哈希→alt 映射：`re.findall(r'!\[([^\]]*)\]\(images/([a-f0-9]{64})\.(?:jpg|...)\)')`
2. 全局补全：pass2 各字段空 alt `![](images/哈希)` → `![alt](images/哈希)`，**跳过无信息 alt**（空 / 「图片」 / 「image」）
3. 定点替换：按 (卷, 题) 定位，正则按「alt 已补形态」书写；散行图注合并成一行完整图注（如「贾湖骨笛（河南出土，距今 8 000 多年）」）+ 空行分隔
4. 图片行后插空行：仅对目标题逐行处理（图片行且下一行非空 → 插空行）
5. 幂等保障：运行前备份 pass2 到独立子目录；替换未命中时若「已修复形态已在文中」则静默跳过、否则报错中止；重跑零改动
6. ⚠ 替换串里的 CDN 来源图哈希不在源 md 本地映射中，需写死完整哈希（与本地 images/ 核对后），不能依赖映射反查

**CDN 嵌选项的配图题**（如「图+A.《作品》+图+B.《作品》…」交替结构）：图片语法嵌在 pass2 选项字段内。build 会自动把选项内图片语法剥离、追加到题干末尾（P 摘出→追加→P 另起一行补回），图片顺序与选项字母序天然对应——**无需手工修复**，build 后抽查即可。

## 二、图片字段空 alt 机制

**机制**：`qb_schema.build_body` 对 `rec["图片"]` 字段的图**硬编码空 alt**（`![](images/name)`）追加到正文尾部；题干中已有的同名引用才去重跳过。

**推论**：
- 题干内的图片行**原样透传**（alt 保留）→ 有信息的 alt 必须补在 **pass2 题干文本内**，补在别处无效；
- 「图片字段来源」的图（pass2 里只有哈希列表、不在题干文本中）走 build_body 硬编码路径 → **alt 必然为空**，gen JSON 中无 alt 位可填。

**兜底**：入库后对 TNote 笔记文件直改——用源 md 哈希→alt 映射，把 `![](images/<哈希>.jpg)` 替换为 `![alt](images/<哈希>.jpg)`（Obsidian 运行中自动索引）。数量通常个位数，一次性脚本即可。

**待改进项**：`build_body` 支持 `{"src","name","alt"}` 三键（alt 缺省空）；`step10_build` 生成图片字段时从源映射传入 alt。改动涉及 skill 共享脚本，启用前需评估影响面。

## 三、孤儿图统计的 CDN 前缀坑

**背景**：MinerU 输出的 images/ 目录常多于源 md 引用数，需要统计「未被引用的孤儿图」以评估缺图能否配对回填。

**坑**：源 md 中图片有两种引用形式：
- 本地：`![alt](images/<64字符>.jpg)`——文件名实为 **60 位 hex + 4 位序号**（共 64 字符）；
- CDN：`![image](https://cdn-mineru.openxlab.org.cn/result/<task>/<64字符>.jpg)`——URL 末段**带 `.jpg` 扩展名**，alt 全为无信息的「image」。

⚠ 直接对 URL 末段套 `[a-f0-9]{64}\)` 或固定长度 hex 正则会因 `.jpg` 后缀漏匹配 → **CDN 图的本地副本全部被误判为孤儿**（实测 41 张中 19 张误判）。

**正确姿势**：抓完整 URL → `os.path.basename` → 从 basename 中 `re.search(r'([a-f0-9]{40,64})')` 提取 hex 段 → 加入 used 集合 → 本地文件名 `startswith(hex段)` 判定引用。

**孤儿图构成的经验判断**：MinerU 对表格区域常**同时输出 HTML 表格与表格截图副本**，md 只引用 HTML 形式 → 孤儿图多为表格/年代尺/文字截图。**配对实物照片前先看孤儿构成**（生成缩略拼贴目检），避免无效配对。

**MinerU vlm 漏检定性**：若某题在源 md 中只有图注文字行、图片块完全缺失（本地图与 CDN URL 均无），且 pass1/pass2 亦无图片引用，则根因 = **MinerU 解析阶段漏检**（识别到图注但未输出图片块）。重新解析可能复现漏检且需重跑全链路；题干文字自含作答信息时，接受现状是合理决策（定性结论记入日志）。
